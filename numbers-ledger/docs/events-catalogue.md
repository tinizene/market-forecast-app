# Africa Numbers — significant events

Every event this system records: what it means, which record it lands in, and
what it carries. Generated by `npm run events` and checked against the code from
two directions on every build.

```
catalogued        42
found in the code 42
observed written  42
transactions      19   double-entered, money moved
events            23   a fact with no money in it
```

**A kind in the code and not on this page fails the build.** So does a kind on
this page and not in the code, and so does one filed under the wrong record. The
check runs the system, watches what it writes, and compares.

Every kind on this page was observed being written while the system was exercised.

## Where an event lives

| | |
| --- | --- |
| **Journal** | A double-entered transaction. Append-only, durable, and the balances are derived from it rather than stored beside it. |
| **Event** | A fact with no money in it — a suspension, a policy change, a PIN lockout. Same store, same durability, same append-only guarantee. |
| **Call log** | One line per HTTP call, to an append-only file. The only record of a *read*. |

## Money

Value moving between the operator, a runner and a player.

### `CAPITAL_INJECTION`

**The operator funds the business** — journal, about a operator.

Settlement funds increase against operator capital. Nothing else in the system creates an asset.

### `BUY_FLOAT`

**A runner buys float** — journal, about a runner.

Money received, float issued, commission recognised as the difference. The only way electronic value enters a runner's hands.

### `SELL_FLOAT_BACK`

**A runner sells float back** — journal, about a runner.

Float returned for real money. The route that keeps a runner in a winning neighbourhood able to pay winners.

### `CASH_IN`

**A player tops up at a runner** — journal, about a player.

Float moves to a wallet. The cash itself is between two people and never appears - the single entry a regulator should look at hardest.

### `CASH_PAYOUT`

**A runner pays a winner in cash** — journal, about a player.

Wallet down, runner float up, commission recognised. The mirror of a top-up.

### `ISSUE_VOUCHER`

**A runner buys voucher inventory** — journal, about a runner.

Float becomes an unredeemed voucher liability. Sold offline, activated later.

### `REDEEM_VOUCHER`

**A player activates a voucher** — journal, about a player.

The voucher liability becomes a wallet balance. This carries the server timestamp, which is what stops an offline sale producing a bet after a draw.

### `TOP_UP_WALLET`

**A player tops up by mobile money** — journal, about a player.

Recognised only when the provider confirms, never when the request is made.

### `WITHDRAW_MOBILE_MONEY`

**A player withdraws directly** — journal, about a player.

The only path where real money leaves the operator. The transfer fee is an operator cost, not a deduction from the player.

### `ACCRUE_GAMING_TAX`

**Gaming tax accrued** — journal, about a operator.

Recognised as an expense and a payable. Not callable by a player, so outside the solvency check.

## Draws

Committing, taking bets, revealing, settling.

### `PLACE_BET`

**A bet is taken** — journal, about a player.

The stake leaves the wallet for unsettled stakes. Refused after the cutoff on the server clock, whatever the request says.

### `DRAW_OPENED`

**A draw is committed** — event, about a operator.

The commitment is published with the opening, cutoff and draw times, and the custody threshold if the seed was sealed. The ordering of this timestamp against the opening time is the whole integrity guarantee.

### `DRAW_REVEALED`

**The seed is revealed** — event, about a operator.

The seed and the resulting number, checked against the published commitment inside the transaction that records them.

### `SETTLE_DRAW`

**A draw settles** — journal, about a operator.

Stakes recognised as revenue, prizes credited to wallets. Winners are decided by the game rules against the revealed number, never by a list handed in.

## Promotions

What a campaign costs and what it promised.

### `ISSUE_FREE_TICKET`

**A promotional ticket is granted** — journal, about a player.

Promotional cost against a callable liability. Refused if the day's budget is spent - the cap is evaluated inside this transaction.

### `REDEEM_FREE_TICKET`

**A promotional ticket is played** — journal, about a player.

It becomes a stake directly and never touches the wallet, so a grant cannot be withdrawn as cash.

### `FUND_JACKPOT`

**The jackpot is funded from a settled draw** — journal, about a operator.

Recognised draw by draw, so an unwon pot is never mistaken for profit and a pot outgrowing settlement funds halts float sales.

### `PAY_JACKPOT`

**The jackpot is won** — journal, about a player.

The pool moves to a wallet. No expense here - it was recognised as the pot was built.

### `PROMO_CAP_SET`

**The daily promotional budget is set** — event, about a operator.

Carries the amount and the staff member who set it, taken from their credentials. "What was the cap in March, and who set it" has an answer here.

### `PROMO_CAP_CLEARED`

**The promotional budget is removed** — event, about a operator.

Different from a cap of zero: this is no limit at all, and the distinction is deliberate.

## Player protection

Limits, exclusions, and who set them.

### `PROTECTION_SET`

**House limits are switched on** — event, about a operator.

Daily stake and loss caps, with the date and the staff member. Nothing is enforced until this is posted.

### `PROTECTION_CLEARED`

**House limits are switched off** — event, about a operator.

Per-player limits and exclusions are untouched, because those are the player's decisions rather than the operator's.

### `PLAYER_LIMIT_SET`

**A player's own limit is set** — event, about a player.

Tighter or looser than the house policy. A player who asks for a limit gets one whether or not a house policy exists.

### `PLAYER_EXCLUDED`

**A player self-excludes** — event, about a player.

With an end date or indefinitely. Survives a new handset, because it attaches to the number rather than the device.

### `PLAYER_REINSTATED`

**An exclusion ends** — event, about a player.

Recorded separately from the exclusion, so a cooling-off period cannot be shortened without leaving a mark.

## Runner control

Who may sell, and from when.

### `AGENT_SUSPENDED`

**A runner is suspended from selling** — event, about a runner.

With a reason. Takes effect inside the same lock every sale is checked against, so it stops the next sale rather than the next audit.

### `AGENT_REINSTATED`

**A runner is reinstated** — event, about a runner.

The pair of events answers how long a runner was out and who ended it.

## Credentials

Tokens and PINs. Never their values.

### `TOKEN_ISSUED`

**A bearer token is issued** — event, about a any.

Records a short digest of the token, the kind of principal, the subject and the expiry - never the token. The digest is what joins this line to a line in the call log.

### `TOKEN_REVOKED`

**A token is revoked** — event, about a any.

Immediate: the next request with it is refused.

### `PIN_SET`

**A player's PIN is set or reset** — event, about a player.

The PIN is scrypt-hashed and never recorded. There is no self-service reset, so every one of these was performed by staff.

### `PIN_FAILED`

**A PIN was wrong** — event, about a player.

With the running count of failures. A cluster across many players is the signature of a credential attack.

### `PIN_LOCKED`

**A PIN locked after repeated failures** — event, about a player.

Three wrong guesses. Durable, so a restart does not forgive an attacker.

### `PIN_OK`

**A failure count is cleared** — event, about a player.

Written only when a correct PIN follows failures, so the log shows the attempt that ended a run rather than every ordinary use.

### `PIN_UNLOCKED`

**A locked player is unlocked by staff** — event, about a player.

The only way out of a lock, and therefore a line a reviewer should expect to see paired with a support ticket.

## Mobile money

The only boundary where this system does not control both sides.

### `MM_REQUESTED`

**A transfer is requested** — event, about a provider.

Written before the provider is called, under a reference this system generated - which is what lets a timed-out request be asked about rather than retried.

### `MM_ACCEPTED`

**The provider accepted the request** — event, about a provider.

Carries the provider's own reference. Acceptance is not confirmation and does not move money.

### `MM_UNRESOLVED`

**The provider did not answer** — event, about a provider.

A timeout or an outage. The money may well be moving, so the request stays open for the next reconciliation sweep rather than being retried.

### `MM_FAILED`

**A transfer failed** — event, about a provider.

Terminal. A reserved disbursement is returned to the wallet - a return, not a reversal, because nothing was ever paid.

### `MM_ANOMALY`

**A callback could not be applied** — event, about a provider.

A wrong amount, an unknown reference, a contradiction of an earlier callback. Nobody's queue unless somebody looks at it, which is why it is an event and not a log line.

### `RESERVE_DISBURSEMENT`

**A payout leaves the wallet and is held** — journal, about a player.

Money out is reserved before the transfer is attempted, so a wallet cannot be spent twice while a payout is in flight.

### `CONFIRM_DISBURSEMENT`

**A payout is confirmed** — journal, about a player.

The held amount leaves settlement funds. Only now has money actually moved.

### `RETURN_DISBURSEMENT`

**A failed payout is returned** — journal, about a player.

Back to the wallet. Recorded as its own kind so a return can never be read as a fresh top-up.

## The call log

One line per HTTP call — reads as well as writes, because "who looked at this
player's wallet" carries the same weight as "who moved money".

| Field | |
| --- | --- |
| `at` | Server time. Never a value from the request. |
| `method, path` | What was called. |
| `status` | What they were told, including refusals. |
| `principalKind, subject` | Who, from their credentials rather than the body. |
| `tokenId` | The same short digest the TOKEN_ISSUED event carries, so the two join without either holding a working credential. |
| `idempotencyKey` | Which attempt this was, so a retry is identifiable as one. |
| `build` | Which software did it. |
| `secret` | Marks the one response whose contents are never recorded: the call that hands over custody shares. |

**Never recorded:** the request body, the response body, the bearer token, a PIN, a custody share.

## What is not recorded

The section a catalogue written by hand never has.

### Most events record what happened, not who did it

Only the two policy events carry the staff member who posted them, taken from their credentials. For everything else - suspending a runner, resetting a PIN, revealing a draw - the actor is in the call log and joined to the event by time and by token digest. A single field on every event would be better, and is the first thing to add.

### The journal is append-only by storage, not by cryptography

Nothing is ever updated in place, balances are derived rather than stored, and a verification pass proves the cache matches the entries. But a writer with database access could still edit history, and nothing in the record would show it. A hash chain over the journal - each entry carrying the digest of the one before - would make that detectable. It is not built.

### The call log is a file, and the events are not

Ledger events are as durable as the money. The call log - which is the only record of a read - is an append-only JSONL file with no rotation, no retention period and no shipping. "Who looked at this player's wallet" is answered by something that can be lost in a way "who moved money" cannot.

### A direct caller leaves no call-log line

Anything driving the operator object directly - a script, a migration, a console session on the host - writes its ledger events but no call-log line, so the actor is unrecorded. Restricting production to the service, and saying so in the access policy, is the answer rather than more logging.

### No retention policy is written down

The ledger keeps everything permanently by construction. Nothing states how long the call log is kept, where it is shipped, or who may read it. That is a policy document, and it does not exist yet.

### Nothing is recorded about the software itself

A failed build verification, a restore from backup, a change to a rate limit or a body cap: none of these produces an event. The build id is stamped on every call-log line, which is where a deployment becomes visible, and that is the whole of it.

### No thresholds, no alerts

A large win, an unusual velocity, a runner reconciling badly for a third day: all of these are derivable from the journal and none of them raises anything. The reports are pull, not push.

### The mobile money simulator ships in the certified build

There is no driver for a real provider yet, so the composition root has nothing else to wire and the simulator is in the runtime tree. Once a real driver exists, a simulator that can stand in for it should be absent from a certified build in the same way and for the same reason that forced draw outcomes are.
